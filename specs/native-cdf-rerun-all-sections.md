# Feature Spec: Rerun CDF for all 13 sections using native FAARFIELD engine (LEAF-only)
Date: 2026-04-21
Layer: analysis-script (+ light data copy to website-frontend)

## What We're Building
Replace the current CDF numbers (computed by the hand-ported Python engine in `scripts/faarfield_engine.py`) with numbers from the **native .NET FAARFIELD desktop-parity engine** served at `POST /api/analysis/cdf`. 3D FEM stays **off** (`useFem3d = false`) — pure LEAF + rigid FEM(AMClassLib) path, which is what "full FAARFIELD engine" means in this project's vocabulary. Regenerate all `results/*_CDF_Full_Output.txt`, `*_CDF_Results.md`, `ALL_CDF_Summary.md`, and `results/cdf_results.json`, then sync that JSON into the website's data folder so the Project Report tab reflects the new numbers.

## Why This Matters
The current results come from a simplified Python engine (Odemark + Westergaard + Burmister, three failure modes, no SCI). The native wrapper `FullAnalysisWrapper.RunCdfAnalysis` is **desktop-parity** — it covers all 10 gaps: SCI-dependent PCC fatigue with FSlopeComp, two-pass `ComputeResponse2` with 1800 longitudinal nodes, rigid FEM via `AMClassLib.ComputeResponse` with `max(LEAF, FEM)` per aircraft, StraightLine + Bleasdale subgrade models, RDEC AC fatigue, WFBF gear splitting, C-5 special case, thickness design, life analysis, multi-subgrade. The report tab should quote *these* numbers, not the Python approximations.

## Files to Create or Edit

- `scripts/all_airports_cdf_native.py` **(new)** — Python driver that loops 13 sections, POSTs `/api/analysis/cdf` with `useFem3d=false`, writes all result files. Mirrors the I/O shape of the existing script so downstream consumers don't break.
- `results/native_vs_python_diff.md` **(new)** — generated by the driver script as a postscript comparison.
- `c:/temp/aeropave/src/data/cdf_results.json` **(overwrite)** — copied from `results/cdf_results.json`.
- *No* backend changes. *No* frontend component changes. *No* Python-side aircraft library — the backend does all resolution.

**Aircraft resolution — backend owns it (non-negotiable).** The Python driver sends only raw Excel fields (`icao`, `mtow`, `gear`, `annualDeps`, `tirePressure` if non-zero, `mgPct` if non-zero). The backend's `FullAnalysisWrapper.RunCdfAnalysis` loops the payload and calls `AircraftLibrary.ResolveGeometry(icao, gear, mtow, tp)` + `AircraftLibrary.BuildLeafParms(...)` internally ([FullAnalysisWrapper.vb:577](c:/temp/aeropave/faarfield-api/FullAnalysisWrapper.vb#L577)) — the **same** library that carries the updated proxy-gear wheel coordinates used by the interactive Design Tool, LEAF stress contour, and 3D FEM viewer. No parallel Python lookup table; no FAA ACD cross-reference on the Python side; no second aircraft library to drift out of sync.

**Gear-coord integrity — audit every aircraft, let tier 3/4 through but flag them.** `AircraftLibrary.ResolveGeometry` ([AircraftLibrary.vb:170-238](c:/temp/aeropave/faarfield-api/AircraftLibrary.vb#L170)) has a 4-tier fallback:

| Tier | `Source` value | What it means | Policy this rerun |
|---|---|---|---|
| 1 | `xml` | Exact FAARFIELD XML `wheel_coords` — real aircraft geometry | ✅ preferred |
| 2 | `proxy_override` | Curated donor (Phenoms, Galaxy, G280) — donor has XML coords | ✅ preferred |
| 2 | `icao_proxy` / `family_proxy` / `nearest_proxy` | Borrowed XML coords from closest real aircraft in library | ✅ preferred |
| 3 | `gear_template` | Hard-coded simplified layout by gear letter (S = single 0,0; D = ±17,0; 2D = ±22×±27.5; etc.) | ⚠️ allowed — **flagged** in results |
| 4 | `dual_fallback` | Generic ±17/0 when gear type unknown | ⚠️ allowed — **flagged** in results |

**Per user instruction: tier 3 and tier 4 are not a hard stop for this rerun.** The driver still audits every aircraft through `GET /api/aircraft/resolve/{icao}?gear=...&mtow=...` (response exposes `geometrySource`, `resolvedIcao`, `nWheels`, `wheelCoords[]`), but the CDF run proceeds for tier-3/4 aircraft. Those aircraft get **visibly noted** everywhere the user might read the results:

- `results/gear_coord_audit.json` — every aircraft with its source, resolvedIcao, wheel count
- `results/ALL_CDF_Summary.md` — dedicated "Aircraft with simplified (template/fallback) wheel layouts" section listing each offender, its airport, its section, its CDF contribution, and the gear template used
- Per-airport `results/<ICAO>_CDF_Results.md` — a callout box if any of that airport's traffic used tier 3/4, plus a column-level asterisk in the top-aircraft table
- `results/cdf_results.json` — each `top_aircraft[]` entry gains `wheelSource` and `wheelSourceNote` fields so the Project Report tab can render the flag
- `results/native_vs_python_diff.md` — notes where simplified coords may explain the old-vs-new delta

Future follow-up (out of scope for this spec): for any aircraft that matters (non-trivial CDF contribution × high annual departures), consider promoting them to XML or `_proxyOverrides` in a later session. For now they just run and get flagged.

## Out of Scope

- **3D FEM (useFem3d=true) rerun** — explicitly skipped per user request. The Design Tool tab continues to auto-run FEM interactively; the *batch* results will be the LEAF-only full engine.
- **Backend changes** — `RunCdfAnalysis` already exposes everything we need.
- **Frontend component changes** — same JSON shape means Project Report tab rendering is unchanged.
- **Thickness design rerun** — this spec is CDF-only (`runMode="cdf"`). Design iteration is a separate feature.
- **Per-aircraft FEM stress columns in the report** — not populated when useFem3d=false; that's fine.
- **Growth formula changes** — we pass the same `growth` values already in the Excel/script. If the native engine's internal projection differs from our Python `[1+Life*g*0.5]*Annual*Life`, we document the delta in the diff report but don't patch either side.
- **Re-running the Python engine** — kept around for reference (`cdf_results_python_backup.json`) but not the source of truth anymore.

## Risks / Watchpoints

- **Traffic sheet volume**: Traffic378 (KMQJ) has ~30 aircraft types. With rigid-FEM evaluation per aircraft via `AMClassLib.ComputeResponse`, expect ~1–3 s per aircraft per section → a KMQJ section ≈ 60–90 s, all 13 sections ≈ 10–15 min total. Script should log progress, not block silently.
- **Aircraft resolution failures**: 208/229 ICAO codes matched FAA ACD (per CLAUDE.md) — the other 21 will fail backend resolution too. Pre-flight step 2 catches them before the slow CDF run. Policy: skip with a warning and record in the diff report; never silently zero-out unmatched traffic.
- **Backend-only resolution**: the Python driver must **not** maintain its own ICAO→MTOW or ICAO→gear table. If the Excel row has a typo (e.g. BE9T MTOW 1,543 instead of 15,430), the backend library's MTOW/gear will be used instead once `ResolveGeometry` fills in the blanks — this is intentional. If the Excel value is *non-zero* for MTOW or tirePressure, the backend treats it as an override. If we want to fully defer, pass `0` in those fields.
- **Subgrade field**: current Python script jams subgrade as the *last layer* with `h=9999`. Native API expects it in a **separate** `subgrade` object. Don't double-count.
- **Backend cache**: `FullAnalysisWrapper` doesn't cache at the request level (Fem3dWrapper does); each POST re-runs from scratch. That's fine for a batch run.
